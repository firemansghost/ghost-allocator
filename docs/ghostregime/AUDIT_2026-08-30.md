## Methodology Findings

### Most important finding — inflation sign semantics

Current inflation core combines four signals into one scalar. In the final score, **positive means Inflation** and **negative means Disinflation**.

Observed implementation in `lib/ghostregime/regimeCore.ts` / `lib/ghostregime/config.ts`:

#### PDBC

Positive vote = Inflation. `TR_63 >= +0.02` adds `+1`; `TR_63 <= -0.02` adds `-1`.

#### TIP/IEF

Positive vote = Inflation. `TR_63 >= +0.005` adds `+1`; `TR_63 <= -0.005` adds `-1`.

#### TLT

Current implementation assigns:

```text
TLT rising strongly (TR_63 >= +0.01) → +1 labeled Disinflation
TLT falling strongly (TR_63 <= -0.01) → -1 labeled Inflation
```

#### UUP

Current implementation assigns:

```text
UUP rising strongly (TR_63 >= +0.01) → +1 labeled Disinflation
UUP falling strongly (TR_63 <= -0.01) → -1 labeled Inflation
```

PDBC/TIP and TLT/UUP therefore use **opposite numeric sign semantics** while being summed into the same scalar. Receipt `direction` labels attempt to compensate (TLT/UUP `+1` is labeled Disinflation), but the numeric votes still add as if `+1` were the same semantic as PDBC/TIP Inflation.

This is an **internal semantic inconsistency**.

**Do not correct it in a documentation or opportunistic code PR.**

For the observed August 28 snapshot:

- core inflation score was `0`
- commodity satellite contributed `+1`
- final inflation score was `+1`

Normalizing TLT/UUP numeric signs on that one day would still leave core inflation at zero and final inflation at `+1`, because the satellite contributed the deciding `+1`. The current live regime would **not necessarily change** from a one-day sign correction.

Historical impact remains **unknown** and must be quantified first.

The next substantive work is **R0 — read-only forensic model-impact audit**.

R0 must determine historically:

- dates where normalized inflation-sign semantics change the inflation axis

Do not authorize production sign changes until R0 is reviewed.

`classifyRegime()` treats `inflScore > 0` as Inflationary and everything else (including `0`) as Disinflationary. That is current behavior, not a finding that the zero-as-Disinflation rule is wrong. R0 should characterize how often ties occur and how satellites/tie-break interact.

## Flip Watch Findings

Public methodology currently presents Flip Watch as if it prevents whipsaw and waits for regime confirmation.

Copy in `lib/ghostregime/ghostregimePageCopy.ts`:

- “It reduces whipsaw by waiting for confirmation.”
- Flip Watch tooltip: “waits for an extra day before treating a regime change as real.”

`docs/ghostregime/PLAN.md` describes a persistence guard: 2-day confirmation unless strong margin (`abs(score) >= 2`).

`docs/ghostregime/VALIDATION.md` lists Flip Watch confirmation/persistence-guard checks as if they are accepted invariants.

Current engine behavior observed in source:

1. Determine the new regime (`classifyRegime`, then optional stress override).
2. Immediately calculate allocations from that new regime.
3. Then calculate `flip_watch_status` via `detectFlipWatch()`.

`shouldApplyFlip()` exists in `lib/ghostregime/flipWatch.ts` and is **not used** by the production regime path. A repository-wide search finds it only in its definition file. Nothing delays the regime or allocation change.

Observed live proof on the August 28 snapshot:

```text
regime: INFLATION
INFLATION targets already active
flip_watch_status: PENDING_CONFIRMATION
```

Current Flip Watch therefore appears to be **telemetry/status**, not an actual regime-transition gate.

`daysSinceLastFlip` in `engine.ts` is:

```text
previousRegime ? differenceInDays(asofDate, new Date()) : 0  // Simplified
```

That does **not** appear to derive from durable prior-flip history. It uses calendar distance from as-of to “now.” Forensic review is required before anyone treats Flip Watch timing as historically meaningful.

Do not fix this now.

Future product gate (no decision is implied by documenting the options):

### Option A — Telemetry only

Rename/correct copy so it truthfully describes what the feature does.

### Option B — Real confirmation

Use historical state to actually delay regime transitions until confirmation rules are satisfied.

Option B is a methodology change and requires historical replay before approval.

## Stress Override Finding

The engine computes `riskAxis` from the pre-override risk score:

```text
riskAxis = riskScore > 0 ? 'RiskOn' : 'RiskOff'
```

Stress override can subsequently force:

```text
risk_regime = RISK OFF
```

and, if the classified regime was GOLDILOCKS or REFLATION, reclassify to INFLATION or DEFLATION. `riskAxis` is **not** recomputed after that override.

This creates the **possibility** of rows whose descriptive axis and final regime disagree (for example `risk_axis: RiskOn` with `risk_regime: RISK OFF` after override).

Treat this as a **characterization/test requirement**, not as a proven historical production failure. This checkpoint did not inspect persisted history for affected rows. R0 should quantify it.

### Public-read / provider-activity finding

This is a high-priority operational issue.

Scheduled refresh has a useful preflight (`evaluateScheduledRefreshPreflight`) that can serve a healthy, schema-current persisted latest snapshot without performing a new market fetch (`refresh_outcome: scheduled_served_persisted_no_fetch`).

Ordinary unauthenticated `GET /api/ghostregime/today` reads, however, currently enter `getGhostRegimeToday()` without that skip. They appear capable of fetching current market/provider data in order to compute as-of and decide whether the persisted snapshot is still current, even when the response ultimately serves the persisted row (`served_persisted_snapshot`).

The public `/ghostregime` page consumes that API (server fetch in `app/ghostregime/page.tsx` and client fetch in `GhostRegimeClient.tsx`).

Recommended future architecture:

```text
normal public read
    → persisted state only
    → no live provider calls
authenticated scheduled refresh
    → conditional compute
authenticated force refresh
    → deliberate compute
controlled debug
    → deliberate compute with explicit authorization
```

This is an operational containment improvement, not a methodology change.

### Paid-provider containment finding

Verified current access control on `/api/ghostregime/today`:

- `force=1` and `refresh=scheduled` require `GHOSTREGIME_CRON_SECRET`.
- `debug=1` did **not** appear equivalently protected during the audit. The route treats debug as an unauthenticated query flag and passes it through to `getGhostRegimeToday(debug, …)`, which recomputes and does not persist.
- Normal public reads can currently reach provider logic, as above.
- Marketstack is normally disabled unless explicitly ALLOW-gated.

Therefore, during a temporary Marketstack emergency-ALLOW window, anonymous traffic (normal page/API reads, or `debug=1`) could potentially reach the paid fallback if free providers failed.

Treat this as a **containment hole to close during R2**. Do **not** describe it as a current Marketstack billing incident. This checkpoint does not claim overage or live paid-fallback use on August 30.

### Error-diagnostic double fetch

The outer engine error path in `getGhostRegimeToday()` appears capable of calling `defaultMarketDataProvider.getHistoricalPrices()` again to assemble diagnostics after an initial provider/compute failure.

Potential consequences:

- duplicate traffic
- repeated calls to unhealthy providers
- potential repeated paid fallback traffic during an emergency ALLOW window

Future recommendation: preserve and propagate first-attempt diagnostics rather than performing another full provider fetch.

No implementation in this checkpoint.

## Persistence Findings

Strong pieces:

- stale/debug rows are not intentionally persisted as current state
- persist gating exists (`getPersistSnapshotRejection` / `isValidPersistableSnapshot`)
- failed/stale computation can preserve last-known-good blob latest
- scheduled freshness preflight exists
- cold-start behavior does not fabricate a fake latest state

Flag for later characterization (do not repair now):

- Schema/current-state checks using truthiness can mis-handle legitimate numeric zero values. `isPersistedRowSchemaOutdated()` treats `!row.infl_total_score_pre_tiebreak` as outdated. A legitimate pre-tiebreak score of `0` would be falsy in JavaScript and could force an unnecessary recompute.
- Persist gate currently checks date, regime, compute metadata, and finite risk/inflation scores. It does not yet enforce allocation / scale / cash sum invariants.
- Some `refresh_outcome` labeling may not precisely distinguish every non-persist case. Persist-gate rejection currently reuses `computed_not_persisted_debug` even when the row is not a debug compute.

## UI / Product Truth Findings

Record these as future **R6** work. Do not implement UI changes in this checkpoint. Do not choose final copy here.

### A. “Hold now”

Current language (`POSTURE_HOLD_NOW_LABEL`, sleeve “Hold now (Actual)” lines) can sound prescriptive for an educational research product. GhostRegime is a posture/education overlay, not the builder allocation driver (existing DECISIONS, 2026-01-21).

Potential future wording (examples only):

### B. `% of Max`

The default view compares actual allocation against **global maximum sleeve allocation** (`getMaxTargets()`: stocks 60, gold 30, BTC 10), not the current regime target.

Example from August 28:

```text
Stocks actual 30 / regime target 30
```

That can display as only 50% of max because global stock max is 60. The math is technically valid and is covered by `maxExposure` tests. It is cognitively misleading for the primary view.

### C. Headline rounding

Observed display:

```text
30 / 8 / 3 + 60 cash
```

which visually totals 101 because 7.5 and 2.5 are rounded independently (`toFixed(0)`). Underlying exact allocations still sum to 100.

### D. BTC Actionable Read bug

Observed live state:

```text
BTC scale = 0.5
BTC actual = 2.5%
```

while UI text indicated:

```text
BTC off → +3% cash
```

This is incorrect. `buildActionableReadLine()` does distinguish half-size vs off, but `components/ghostregime/ActionableReadPills.tsx` hard-codes `Bitcoin off → +N% cash` whenever `cashFromBtc > 0.001`, regardless of scale. Half-size BTC (5% target × 0.5 = 2.5% actual) therefore releases 2.5% to cash and can display as “off → +3% cash” after rounding.

### E. Coverage semantics

All four risk signal data series were present on the observed day, but three were neutral. UI reported:

```text
Risk Coverage 1/4
```

`computeAxisStats()` measures `nonNeutral / totalSignals`. Tooltip copy (`COVERAGE_TOOLTIP`, `LEGEND_COVERAGE`) implies availability / expected signals (“Signals available / signals expected (some can be missing)”).

This appears to measure **active / non-neutral signals**, not data availability.

### F. Neutral receipts

`deriveVotedLabel()` can render vote `0` as Neutral. The persisted receipt `direction` field from `computeOptionBVotes()`, however, uses `vote > 0 ? 'Risk On' : 'Risk Off'` (and the inflation analogue). Vote `0` is therefore stored as a negative-side direction such as `Risk Off` rather than explicit Neutral. UI surfaces that consume `receipt.direction` can show the wrong label.

### G. Vocabulary overload

The current public page exposes many overlapping concepts:

- agreement
- coverage
- confidence
- conviction
- regime confidence
- regime conviction
- crowded
- primary driver
- pressure
- confirmation

Later UI work should simplify hierarchy after semantics are corrected.

### H. Pressure Watch vs Flip Watch

`flipWatchPressure.ts` is display-only axis/sleeve pressure versus the prior persisted row. `flip_watch_status` is (intended) regime-change confirmation. Existing DECISIONS (2026-03-24) already separate those.

Avoid using “flip” for both sleeve-state threshold changes and regime confirmation. Future terminology should distinguish sleeve **state change** from regime **flip**.
